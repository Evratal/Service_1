# Схема базы данных сервиса записи

Документ описывает базу данных проекта **TOP BRO** — сервиса онлайн-записи к мастерам.
Источники: паспорт продукта (`docs/product-passport.md`) и прототип клиентского пути
(`prototype/`, три экрана: лендинг, форма записи, подтверждение).

Движок: **SQLite** через встроенный модуль Node.js `node:sqlite`.
Схема зафиксирована в миграциях: `migrations/001_init.sql` (основные таблицы)
и `migrations/002_notifications.sql` (уведомления).

---

## 1. Как экраны превращаются в таблицы

Структура базы выведена из данных, которые показывает каждый экран прототипа.

| Экран / сценарий | Какие данные показывает | Таблицы |
|---|---|---|
| Лендинг | услуги с ценой и длительностью, мастера, адрес, часы работы, телефон | `salon`, `services`, `masters` |
| Регистрация и вход | e-mail, имя, хеш пароля, роли, токен доступа | `users`, `user_roles`, `auth_tokens`, `login_attempts` |
| Выбор услуги | название, длительность, цена, активна ли услуга | `services` |
| Выбор мастера | имя, специализация, какие услуги выполняет мастер | `masters`, `master_services` |
| Выбор даты и времени | график мастера на день, занятые интервалы, блокировки | `schedules`, `time_blocks`, `appointments` |
| Подтверждение записи | клиент, мастер, услуги, время начала и окончания, статус, сумма | `appointments`, `appointment_services` |
| Личный кабинет | записи, отфильтрованные по клиенту и статусу | `appointments` |
| Панель администратора | все записи, услуги, мастера | `appointments`, `services`, `masters` |
| Уведомления (счётчик в шапке) | число непрочитанных сообщений пользователя | `notifications` |
| Страница «Уведомления» | текст события, связанная запись, прочитано/нет | `notifications`, `appointments` |

Общий принцип: **один факт хранится в одном месте**. Имя мастера лежит в `masters`,
цена услуги — в `services`. В `appointments` хранятся только ссылки (`master_id`) и
значения, которые принадлежат именно этой записи (время, статус).

## 2. Соглашения

### Типы полей

| Тип | Для чего |
|---|---|
| `INTEGER` | целое число: идентификаторы, длительность, сумма |
| `TEXT` | строки: имена, e-mail, статусы |
| `INTEGER` + `CHECK (x IN (0,1))` | логический флаг: `is_active`, `is_override` |

В SQLite нет отдельного типа для «да/нет», поэтому флаги хранятся числами:
`1` — да, `0` — нет.

### Даты и время

В SQLite нет типа даты, поэтому все моменты времени хранятся **текстом в формате
`YYYY-MM-DDTHH:MM:SSZ`** — всегда в UTC, с обязательной буквой `Z`.

Такой формат выбран потому, что текст в едином формате можно сравнивать и сортировать
строковыми операциями: `"2026-09-28T12:00:00Z" < "2026-09-28T13:00:00Z"` даёт верный
результат. Если записывать даты произвольно (`28.09.2026`, `28 сентября`), сравнение
сломается.

Время в `schedules` — исключение: это не момент времени, а **расписание по дням недели**,
поэтому там хранится день недели и локальное время салона в формате `HH:MM`. Перевод
локального времени салона в UTC выполняет сервер в момент расчёта, используя часовой
пояс из таблицы `salon`.

### Деньги

Цены хранятся **целым числом рублей** в поле `price_rub`. Копейки в проекте не
используются, поэтому дробные значения не нужны, а ошибки округления исключены.
Итоговая стоимость записи не хранится — она вычисляется как сумма цен услуг
из `appointment_services` (см. раздел 5).

### Обязательность

В описании каждого поля указано: **«Да»** — поле обязательно, **«Нет»** — может быть пустым (`NULL`).

## 3. Таблицы

Всего **13 таблиц**. У каждой есть первичный ключ, все связи оформлены внешними ключами.

---

### 3.1 `users` — пользователи сервиса

Клиенты, мастера и администраторы в одной таблице: у них общий набор данных
(e-mail, имя, вход).

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `email` | TEXT | Да | Логин, уникальный, хранится в нижнем регистре |
| `password_hash` | TEXT | Да | `scrypt$N$r$p$salt$hash`. Самого пароля в базе нет |
| `name` | TEXT | Да | Имя, показывается в кабинете и админ-панели |
| `phone` | TEXT | Нет | Необязательный телефон для связи |
| `is_active` | INTEGER | Да | `1` — может входить, `0` — заблокирован |
| `created_at` | TEXT | Да | Момент регистрации, UTC |

Связи: `1 → N` в `user_roles`, `masters`, `appointments` (как клиент), `auth_tokens`.

**Почему нет поля `password`.** Хранится только `password_hash` — необратимо
преобразованная строка. Проверить правильность пароля по ней можно, восстановить
исходный пароль — нет. Если копия базы попадёт в чужие руки, пароли не утекут.

---

### 3.2 `user_roles` — роли пользователя

Отдельная таблица, потому что у одного человека может быть несколько ролей
(владелец студии часто ещё и мастер, и администратор).

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `user_id` | INTEGER | Да | Внешний ключ → `users.id` |
| `role` | TEXT | Да | `client` / `master` / `admin`, `CHECK` ограничивает значения |

Первичный ключ: составной `(user_id, role)`.
Ограничение `CHECK (role IN ('client','master','admin'))` — база физически не пропустит
выдуманную роль, даже если ошибка появится в коде.

**Почему не строка `roles` со списком.** Список в JSON-тексте нельзя проверить
ограничением `CHECK`, и поиск роли приходится делать в коде. Отдельная таблица
позволяет базе самой гарантировать корректность и искать роль обычным `EXISTS`.

---

### 3.3 `salon` — данные студии

Одна строка: название, адрес, телефон, часы работы, часовой пояс.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Всегда `1` |
| `name` | TEXT | Да | Название студии |
| `timezone` | TEXT | Да | IANA-зона, например `Europe/Moscow` |
| `address` | TEXT | Да | Адрес из подвала лендинга |
| `phone` | TEXT | Да | Телефон для связи |
| `work_start` | TEXT | Да | Открытие, `HH:MM` локального времени |
| `work_end` | TEXT | Да | Закрытие, `HH:MM` |

**Почему в базе, а не в `.env`.** Часовой пояс и адрес меняет администратор студии,
а не разработчик. Настройки продукта, которые может менять владелец, должны лежать
в базе. В `.env` остаются только секреты (см. `.env.example`).

Часовой пояс нужен, чтобы «15:00» на экране клиента и `12:00Z` в базе описывали
один и тот же момент, а расписание мастера не съезжало на час.

---

### 3.4 `masters` — профили мастеров

Профессиональные данные отдельно от `users`, иначе у клиентов и администраторов
большинство полей было бы пустым.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `user_id` | INTEGER | Да | Внешний ключ → `users.id`, `UNIQUE` |
| `specialization` | TEXT | Да | Короткая специализация: «Барбер, стаж 8 лет» |
| `bio` | TEXT | Нет | Описание мастера для карточки |
| `is_active` | INTEGER | Да | `1` — принимает записи, `0` — скрыт |

`user_id` уникален: у мастера ровно один профиль, а у пользователя — не больше одного.

---

### 3.5 `services` — услуги

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `name` | TEXT | Да | Название услуги |
| `description` | TEXT | Нет | Текст карточки на лендинге |
| `duration_min` | INTEGER | Да | Длительность в минутах, `CHECK > 0` |
| `price_rub` | INTEGER | Да | Цена целым числом рублей, `CHECK >= 0` |
| `is_active` | INTEGER | Да | `1` — видна клиентам, `0` — скрыта |
| `created_at` | TEXT | Да | Момент создания, UTC |

---

### 3.6 `master_services` — какие мастера выполняют какие услуги

Связь **многие-ко-многим**: один мастер выполняет много услуг, одну услугу выполняют
разные мастера. Одним полем такую связь выразить нельзя.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `master_id` | INTEGER | Да | Внешний ключ → `masters.id` |
| `service_id` | INTEGER | Да | Внешний ключ → `services.id` |

Первичный ключ: составной `(master_id, service_id)` — он же уникальное ограничение,
запрещающее добавить одну пару дважды.

Используется на экране «Выбор мастера»: клиент отметил стрижку и камуфляж — сервис
показывает только мастеров, у которых есть **обе** услуги.

---

### 3.7 `schedules` — регулярный график работы

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `master_id` | INTEGER | Да | Внешний ключ → `masters.id` |
| `weekday` | INTEGER | Да | `0` — воскресенье … `6` — суббота, `CHECK 0..6` |
| `start_time` | TEXT | Да | Начало работы, `HH:MM` местного времени |
| `end_time` | TEXT | Да | Конец работы, `HH:MM` |
| `is_working` | INTEGER | Да | `1` — работает в этот день, `0` — выходной |

Уникальное ограничение `(master_id, weekday)` — на каждый день недели у мастера
не больше одной строки, иначе график задублируется бы.

**Это не слоты.** Строка отвечает на вопрос «когда мастер вообще работает»,
а не «когда есть свободное время». Свободное время вычисляется (раздел 5).

---

### 3.8 `time_blocks` — разовые блокировки

Перерывы, отпуска, обучение, санитарный день. В отличие от `schedules`,
блокировка действует один конкретный период, а не повторяется каждую неделю.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `master_id` | INTEGER | Да | Внешний ключ → `masters.id` |
| `starts_at` | TEXT | Да | Начало блокировки, UTC |
| `ends_at` | TEXT | Да | Конец блокировки, UTC |
| `reason` | TEXT | Нет | «Обед», «Отпуск» |
| `created_by` | INTEGER | Да | Внешний ключ → `users.id`, кто создал |
| `created_at` | TEXT | Да | Момент создания, UTC |

`CHECK (ends_at > starts_at)` — блокировка не может иметь нулевую или отрицательную длину.

---

### 3.9 `appointments` — записи

Центральная таблица сервиса.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `client_id` | INTEGER | Да | Внешний ключ → `users.id`, кто записался |
| `master_id` | INTEGER | Да | Внешний ключ → `masters.id`, к кому записались |
| `starts_at` | TEXT | Да | Начало визита, UTC |
| `ends_at` | TEXT | Да | Конец визита, UTC |
| `status` | TEXT | Да | Одно из: `booked`, `completed`, `cancelled_by_client`, `cancelled_by_salon`, `no_show` |
| `is_override` | INTEGER | Да | `1` — администратор разрешил наложение на занятое время |
| `created_by` | INTEGER | Да | Внешний ключ → `users.id`, кто создал запись |
| `created_at` | TEXT | Да | Момент создания, UTC |
| `cancelled_at` | TEXT | Нет | Момент отмены, `NULL` у активной записи |
| `cancel_reason` | TEXT | Нет | Причина отмены |
| `notes` | TEXT | Нет | Пожелания клиента |

`CHECK (ends_at > starts_at)` — визит без длительности невозможен.
`CHECK (status IN (...))` — свободный текст в статусе запрещён, иначе появятся
`cancelled`, `Cancelled`, `отменена` и фильтры перестанут работать.

**Поле `ends_at` обязательно.** Без него сервис не знает, до какого момента мастер
занят, и не сможет посчитать свободные интервалы: визит 15:00–17:00 занимает два часа,
а не один слот.

**Поле `is_override`** нужно для разрешённого исключения: клиент пришёл без записи,
администратор вручную добавляет визит поверх занятого времени. Триггер пересечения
пропускает такую запись, но она сама занимает время как обычная. Выставить признак
может только роль `admin` — это проверяется в API, значение из запроса не принимается.

**Стоимости здесь нет.** Она вычисляется из цен услуг (раздел 5).

---

### 3.10 `appointment_services` — услуги в записи

Одна запись может включать несколько услуг (стрижка + борода), и одна услуга
встречается во многих записях — снова связь многие-ко-многим.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `appointment_id` | INTEGER | Да | Внешний ключ → `appointments.id` |
| `service_id` | INTEGER | Да | Внешний ключ → `services.id` |

Первичный ключ: составной `(appointment_id, service_id)`.

---

### 3.11 `auth_tokens` — токены доступа

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `user_id` | INTEGER | Да | Внешний ключ → `users.id` |
| `token_hash` | TEXT | Да | `UNIQUE`. SHA-256 от токена, `UNIQUE` |
| `expires_at` | TEXT | Да | Момент истечения, UTC |
| `created_at` | TEXT | Да | Момент выдачи, UTC |
| `revoked_at` | TEXT | Нет | Отзыв токена при выходе |

**В базе лежит только хеш токена.** Сам текст токена возвращается клиенту один раз
при входе и больше нигде не сохраняется. Даже если база утечёт, войти чужим токеном
не получится — сервер сравнивает хеш.

Срок жизни ограничен (`expires_at`), поэтому украденный токен перестаёт работать
через заданное время.

---

### 3.12 `login_attempts` — ограничение попыток входа

Защита от подбора пароля перебором.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `email` | TEXT | Да | Какой e-mail пытались войти |
| `ip` | TEXT | Нет | Адрес клиента |
| `succeeded` | INTEGER | Да | `1` — вход удался, `0` — нет |
| `created_at` | TEXT | Да | Момент попытки, UTC |

Индекс по `(email, created_at)` — сервер считает неудачные попытки за последние
15 минут одной выборкой, без сканирования таблицы.

---

### 3.13 `notifications` — уведомления пользователей

Появляются, когда администратор меняет чужую запись: отменяет, переносит
или создаёт поверх занятого времени. Уведомление о собственных действиях клиента
не создаётся — если клиент сам записался или отменил, он и так знает, что сделал.

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `id` | INTEGER | Да | Первичный ключ |
| `user_id` | INTEGER | Да | Внешний ключ → `users.id`, кому адресовано |
| `appointment_id` | INTEGER | Нет | Внешний ключ → `appointments.id`, к какой записи относится; `NULL`, если запись удалена |
| `kind` | TEXT | Да | Короткий код события: `appointment_created` / `appointment_cancelled` / `appointment_rescheduled` / `appointment_override` |
| `title` | TEXT | Да | Заголовок: «Запись отменена» и т.п. |
| `message` | TEXT | Да | Готовый текст для показа — собирается на сервере, чтобы клиент не придумывал формулировки сам |
| `is_read` | INTEGER | Да | `1` — прочитано, `0` — нет |
| `created_at` | TEXT | Да | Момент создания, UTC |

**Почему `kind` и `message` раздельно.** `kind` — машиночитаемый код события,
по которому сервер, например, помечает запись в личном кабинете. `message` —
человекочитаемый текст, который меняется вместе с языком интерфейса, не трогая код.
При одной и той же логике события (той же `kind`) текст можно уточнять без миграции.

**Как появляется запись.** Уведомление создаётся в той же транзакции, что и изменение
записи (см. `src/notify.js`), поэтому либо меняется запись и рядом появляется
уведомление, либо не происходит ничего. Потери события при сбое нет.

## 4. Связи между таблицами

```
users ──1:N──> user_roles
  │
  ├─────1:1──> masters ──1:N──> schedules
  │              │      └─────1:N──> time_blocks
  │              │
  │              └─────N:M──> services        (через master_services)
  │
  ├─────1:N──> auth_tokens
  ├─────1:N──> notifications ──N:1──> appointments (appointment_id, ON DELETE SET NULL)
  └─────1:N──> appointments ──N:M──> services (через appointment_services)
                      │
                      └─────1:N──> time_blocks (накладка, проверяет триггер)
```

**Пример связи, которую разберём в отчёте:** `appointments.client_id → users.id`.
Это связь один-ко-многим: у клиента может быть много записей, а у записи ровно один
клиент. Связь нужна, чтобы по экрану «Мои записи» показать визиты конкретного
человека, а при проверке прав убедиться, что запись принадлежит тому, кто её запросил.
Без этой связи невозможно ни построить личный кабинет, ни закрыть доступ к чужой записи.

Вторая по важности — `master_services`: она связывает мастеров и услуги, потому что
одним полем связь «многие-ко-многим» не выражается.

## 5. Что вычисляется, а не хранится

### 5.1 Свободные слоты мастера

**Главное вычисляемое значение.** В базе нет таблицы свободного времени и не должно
быть: если мастер изменит график, услуга станет длиннее или закончится период,
такую таблицу пришлось бы пересобирать, и она быстро перестала бы соответствовать
реальному расписанию.

Свободный слот — результат вычисления в момент запроса `GET /api/masters/:id/slots?date=YYYY-MM-DD`:

1. Берём рабочий интервал мастера на этот день недели из `schedules`.
   Если строки нет или `is_working = 0` — свободного времени нет.
2. Переводим локальное время салона в UTC по `salon.timezone`.
3. Вычитаем интервалы активных записей из `appointments`
   (статус `booked`) и локальные `time_blocks`, попадающие на этот день.
4. Разрезаем оставшееся время на окна длительностью выбранной услуги.
   Услуги не выбраны — режем с шагом 30 минут.
5. Из результата исключаем слоты, которые прямо сейчас удерживает другой пользователь
   (временное резервирование на 5 минут при оформлении).

Пример: график мастера 10:00–20:00, запись 12:00–13:00, блокировка 15:00–16:00,
услуга 60 минут → свободные окна: 10:00, 11:00, 13:00, 14:00, 16:00, 17:00, 18:00, 19:00.

### 5.2 Итоговая стоимость записи

Не хранится. Считается как `SUM(services.price_rub)` по строкам
`appointment_services` записи. Если администратор поменяет цену услуги, во всех
исторических записях пересчитается новая цена — и это осознанное решение:
хранить цену на момент записи можно, но для MVP это лишнее поле, которое придётся
синхронизировать вручную.

### 5.3 Суммарная длительность записи

Считается как `SUM(services.duration_min)`. При создании записи из этой суммы
получается `ends_at` — то есть длительность вычисляется один раз и сразу
фиксируется в записи, а в таблице услуг остаётся единственный источник правды.

### 5.4 Список свободных слотов рядом с ошибкой 409

При конфликте записи API пересчитывает слоты того же мастера и возвращает
несколько ближайших, чтобы клиент сразу выбрал другое время.

## 6. Уникальные ограничения и индексы

| Ограничение / индекс | Где | Зачем простыми словами |
|---|---|---|
| `UNIQUE(email)` | `users` | Без этого регистрировались бы дубликаты e-mail, и вход работал бы непредсказуемо |
| `UNIQUE(user_id)` | `masters` | У одного человека не может быть два профиля мастера |
| `UNIQUE(user_id, role)` | `user_roles` | Нельзя выдать одну и ту же роль дважды |
| `UNIQUE(master_id, weekday)` | `schedules` | На один день недели — одна строка графика, без дублей |
| `UNIQUE(token_hash)` | `auth_tokens` | Один токен — одна строка; защищает от коллизий |
| `PRIMARY KEY (master_id, service_id)` | `master_services` | Пара «мастер + услуга» не повторяется |
| `PRIMARY KEY (appointment_id, service_id)` | `appointment_services` | Одна услуга не добавляется в запись дважды |
| Индекс `appointments(master_id, starts_at)` | `appointments` | Расчёт свободного времени и проверка пересечений — самая частая операция; без индекса база перебирает все записи |
| Индекс `appointments(client_id, starts_at)` | `appointments` | Экран «Мои записи» |
| Индекс `appointments(status)` | `appointments` | Фильтр активных и отменённых записей |
| Индекс `time_blocks(master_id, starts_at)` | `time_blocks` | Выбор блокировок на день |
| Индекс `schedules(master_id, weekday)` | `schedules` | Поиск графика на день |
| Индекс `login_attempts(email, created_at)` | `login_attempts` | Подсчёт неудачных попыток входа |
| Индекс `notifications(user_id, created_at)` | `notifications` | Лента уведомлений пользователя |
| Индекс `notifications(user_id, is_read)` | `notifications` | Счётчик непрочитанных в шапке |
| Индекс `auth_tokens(token_hash)` | `auth_tokens` | Поиск токена при каждом запросе |

**Почему одного `UNIQUE (master_id, starts_at)` мало.** Такое ограничение поймает две
записи, начинающиеся в 15:00. Но если есть визит 15:00–16:00, а второй начинается
в 15:30, время начала не совпадёт — а интервалы пересекутся. Двойная запись пройдёт.
Поэтому пересечение проверяет **триггер** в базе, а уникальное ограничение на
`(master_id, starts_at)` добавлено как дополнительный дешёвый уровень защиты
(раздел 7).

## 7. Защита от двойной записи на уровне базы

Пересечение считается так: визит А занимает `[A.start, A.end)`, визит Б — `[B.start, B.end)`.
Интервалы пересекаются, если `A.start < B.end` **и** `A.end > B.start`.

Правило строгое (`<`, `>`), а не нестрогое (`<=`, `>=`): визиты 15:00–16:00 и
16:00–17:00 стоят вплотную и **не** считаются конфликтом — второй клиент приходит
ровно в момент окончания первого.

Защита стоит на трёх уровнях, каждый закрывает своё:

1. **API** — до вставки проверяет занятость и возвращает человеку понятное сообщение
   с кодом `409` и списком ближайших свободных слотов. Не защищает от гонки,
   но даёт хороший ответ пользователю.
2. **Транзакция** — `BEGIN IMMEDIATE` сразу берёт блокировку на запись, а не
   переходит к ней при первой вставке. Между `BEGIN` и первой вставкой
   второй запрос уже не может вклиниться. Обычная `BEGIN` (отложенная) для этой
   задачи недостаточна.
3. **Триггер** в базе — `appointments_no_overlap_insert` и `appointments_no_overlap_update`
   проверяют пересечение в момент записи, когда база видит все актуальные данные.
   Это окончательная гарантия: даже если обойти API и вставить строку напрямую,
   база не пропустит пересечение.

Триггеры **пропускают** записи: с `status`, отличным от `booked` (отменённые
и завершённые слот не блокируют), и с `is_override = 1` (осознанное наложение
администратора).

## 8. Спорные решения

### 8.1 Таблица `audit_log` не создана

В примере конспекта журнал действий есть. У нас его нет **намеренно**: панель
администратора (урок 5.5) хранит историю изменений в уведомлениях клиента,
а полноценный аудит всех действий администратора выходит за рамки MVP.

Уведомления, в отличие от журнала, создаются в той же транзакции, что и изменение
записи: клиент не может остаться без события «запись отменена». Журнал действий
администратора добавим, если появится требование «показывать, кто и когда изменил
запись» — как отдельную таблицу с `user_id`, `action` и `created_at`.

### 8.2 Роли в отдельной таблице, а не списком в строке

Требование безопасности говорит «храни роли списком». Реализовано как отдельная
таблица `user_roles`, а не JSON-массив в поле `users`. Причина: `CHECK` в базе
физически запрещает недопустимое значение, а проверка роли делается запросом
`EXISTS`. С JSON пришлось бы разбирать строку в коде на каждом запросе —
и любая ошибка разбора становится ошибкой доступа.

### 8.3 Стоимость записи не сохраняется

Цена услуги может измениться после визита. Если хранить итог в записи, придётся
дублировать цену и решать, какую из двух показывать. Считаем на лету из
`appointment_services`. Плата за это: если цена услуги изменится, в истории
посетителей покажется новая цена. Для MVP это приемлемо; при росте продукта
добавим `appointments.price_snapshot_rub`, заполняемый в момент записи.

### 8.4 Время хранится в UTC, а график — в местном времени студии

Моменты времени (`starts_at`, `expires_at`) — всегда UTC с `Z`. График
`schedules` — местное время студии в `HH:MM`, потому что «мастер работает с 10:00
до 20:00» — это утверждение о студии, а не о конкретном моменте. Пересчёт при смене
часового пояса студии — одна правка в `salon.timezone`.

### 8.5 `is_override` разрешён только для роли `admin`

В прототипе и паспорте такого сценария нет: паспорт ограничивает сервис записью
и отменой. Поле добавлено, потому что конспект явно предусматривает исключение
для администратора, а закрыть его на уровне «не делаем совсем» значит запретить
легитимное действие («клиент пришёл без записи»). Проверка роли — в API, значение
из тела запроса вырезается до вставки.

### 8.6 Права задаются тремя независимыми проверками

Не одной универсальной. На каждом эндпоинте проверяются: авторизован ли пользователь,
есть ли у него нужная роль, принадлежит ли ему запрошенный объект. Первая и вторая
одинаковы для всех, третья разная: клиент видит только свои записи, мастер — своё
расписание, администратор — всё. Объединение в одну проверку дало бы либо дыру
в правах, либо нечитаемый код.

### 8.7 Нет отдельной таблицы для «удержания слота»

Временное резервирование на 5 минут (экран подтверждения с таймером) держим
в памяти процесса: это короткоживущее состояние, терять его при перезапуске
не страшно — клиент просто выберет слот заново. Запись в базу потребовала бы
строки, которая сама по себе является «зарезервированным временем», и усложнила бы
расчёт свободного времени. Оговорка: при нескольких процессах сервера резервирование
перестанет работать. На VPS с одним процессом (урок 5.6) ограничения не проявятся.

### 8.8 `duration_min` в минутах, а не в секундах

Минуты — единица, в которой услуги реально продаются («60 минут»). Если позже
понадобится точность до минуты, добавится `duration_sec`; пересчёт минут
неломающий. Обратное (секунды → минуты) потребовало бы округления на каждом шаге.

## 9. Проверка целостности

SQLite по умолчанию **не проверяет внешние ключи**. Без `PRAGMA foreign_keys = ON`
база примет запись, ссылающуюся на несуществующего мастера, и ошибка всплывёт
позже и в другом месте. Подключение выполняется в `src/db.js`, и эта строка
обязана выполняться при **каждом** открытии базы, а не один раз при запуске.

Ожидаемый результат проверки: попытка создать запись с `master_id = 999` при
несуществующем мастере отклоняется базой с ошибкой `FOREIGN KEY constraint failed`.
