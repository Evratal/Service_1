# Чек-лист ручной проверки сервиса

Проверка проводится вручную пользователем. Результаты записываются в поле
«Результат» каждого сценария после фактического прогона. Ожидаемый результат
описан так, чтобы его можно было увидеть на экране.

Источники сценариев: паспорт продукта (`docs/product-passport.md`), журнал
разработки (`docs/development-log.md`), анализ клиентского пути и админ-панели.

**Как проводить:**
- пройти весь список по порядку, записывая только фактические наблюдения;
- сценарии, требующие двух одновременных пользователей, помечены **[два окна]** —
  обычное окно браузера + окно в режиме инкогнито (2 сеанса);
- найденные проблемы не исправлять до конца прогона — внести в раздел «Находки».

---

## 1. Гость

**1.1. Лендинг открывается и заполнен данными**
- Роль: гость (без входа).
- Действие: открыть главную страницу.
- Ожидаемый результат: услуги и мастера загружаются из базы (видны название,
  цена, длительность услуги; имя и специализация мастера); нет пустых карточек.
- Результат: Пройдено (OK). Услуги и мастера загружены из API, карточки заполнены, пустых карточек нет.

**1.2. Запрос к закрытому разделу без входа**
- Роль: гость.
- Действие: открыть приложение и перейти по адресу личного кабинета
  или уведомлений.
- Ожидаемый результат: вместо записей и уведомлений гость видит сообщение
  «Чтобы видеть записи, войдите в аккаунт» со ссылкой на вход; закрытые
  данные не показываются.
- Результат: OK. По `#/mine` и `#/notifications` показано сообщение с призывом войти. Данные не отображаются.

**1.3. Открыть адрес админ-панели вручную** — сценарий из отчёта Task_4
- Роль: гость (без входа).
- Действие: ввести в адресной строке адрес админ-панели.
- Ожидаемый результат: сервис перенаправляет на страницу входа и не показывает
  закрытые данные.
- Результат: OK. При переходе по `#/admin` неавторизованный пользователь попадает на форму входа (redirectAfterLogin сохранён), админ-раздел не отображается.

**1.4. Регистрация с уже занятым e-mail**
- Роль: гость.
- Действие: на форме регистрации ввести e-mail, который уже есть в базе.
- Ожидаемый результат: появляется понятное сообщение, что такой e-mail уже
  зарегистрирован; вход в личный кабинет не происходит.
- Результат: OK. При попытке регистрации с `anna@example.com` показано сообщение об ошибке (e-mail уже существует), вход не выполнен.

**1.5. Регистрация с пустыми обязательными полями**
- Роль: гость.
- Действие: на форме регистрации оставить пустым имя, e-mail или пароль
  и отправить форму.
- Ожидаемый результат: появляется сообщение о незаполненных полях, запись
  не создаётся.
- Результат: OK. Браузерная валидация блокирует отправку пустых обязательных полей (required/minlength). Запрос не отправляется.

**1.6. Регистрация и вход нового пользователя**
- Роль: гость.
- Действие: зарегистрироваться с новыми именем и e-mail, затем выйти
  и войти снова.
- Ожидаемый результат: после регистрации выполнен вход — в шапке появляется
  имя пользователя и ссылка «Мои записи»; личный кабинет открывается и пуст.
  После выхода и повторного входа — тот же кабинет.
- Результат: OK. Зарегистрирован новый пользователь (самостоятельный выбор имени/email). После регистрации выполнен вход, в шапке отображается имя и ссылка «Уведомления»/«Мои записи», кабинет пуст. После выхода и повторного входа доступ восстановлен.

> Примечание: паспорт продукта (функция 1) обещает восстановление пароля,
> но ни формы «Забыли пароль», ни эндпоинта восстановления в проекте нет —
> это непокрытая функциональность, а не дефект текущей проверки. Сценарий
> в чек-лист не включён; при желании его можно добавить отдельной задачей.

## 2. Клиент

**2.1. Полный путь записи — услуга, мастер, время, подтверждение**
- Роль: клиент (после входа).
- Действие: выбрать услугу и мастера (мастера фильтруются по услугам),
  выбрать дату, свободный слот, подтвердить запись.
- Ожидаемый результат: появился экран подтверждения с временем и услугой;
  после подтверждения запись появляется в личном кабинете без обновления
  страницы.
- Результат: OK. Путь пройден: мастер фильтруется по выбранным услугам, выбран слот, показан экран подтверждения с временем/услугами/итогом. После перехода в «Мои записи» новая запись отображается.

**2.2. Свободные слоты соответствуют рабочему графику мастера**
- Роль: клиент.
- Действие: открыть выбор времени у мастера с видимым графиком.
- Ожидаемый результат: слоты не выходят за рамки рабочего дня мастера
  (время окончания визита не позднее закрытия), в выходной день слотов нет.
- Результат: OK. Слоты доступны в рабочие дни, в выходные (дни без работы мастера) показывается «В этот день мастер не работает». Время окончания визита укладывается в рабочий интервал.

**2.3. Ввод неверного пароля**
- Роль: клиент.
- Действие: на форме входа ввести неверный пароль к существующему e-mail.
- Ожидаемый результат: на форме появляется понятное сообщение об ошибке;
  личный кабинет не открывается.
- Результат: OK. Показано сообщение «Неверный e-mail или пароль», вход не выполнен, кабинет не открыт.

**2.4. Клиент отменяет свою запись**
- Роль: клиент.
- Действие: в личном кабинете открыть будущую запись и нажать «Отменить».
- Ожидаемый результат: запись получает пометку «отменена», освободившийся слот
  снова появляется в списке свободного времени того же мастера.
- Результат: OK. После нажатия «Отменить» запись помечается как «Отменена клиентом», освободившийся слот появляется при повторном просмотре доступного времени у того же мастера.

**2.5. Два клиента записываются на один и тот же свободный слот** —
сценарий из отчёта Task_4 **[два окна]**
- Роль: два клиента (окно 1 и окно инкогнито — второй клиент).
- Действие: первый клиент выбирает свободный слот и доходит до подтверждения;
  второй клиент выбирает тот же слот; первый подтверждает; затем подтверждает
  второй.
- Ожидаемый результат: запись создаётся у первого; второй получает понятное
  сообщение, что время занято, и обновленный список свободного времени, из
  которого этот слот исчез.
- Результат: Пройдено (OK). Запись создана у первого. Второй получил понятное сообщение («Это время больше недоступно. Выберите другой слот.»), список слотов обновился, слот исчез. Двойная запись не создана.

**2.6. Подставлен идентификатор чужой записи**
- Роль: клиент.
- Действие: в адресе личного кабинета подставить идентификатор записи другого
  клиента (найти его, например, по уведомлению об отмене).
- Ожидаемый результат: сервис отказывает в доступе и не показывает имя, телефон
  и другие данные владельца записи.
- Результат: OK. Клиент при попытке доступа к записи другого пользователя получает отказ (запись не отображается, доступ ограничен). Чужие данные не показаны.

**2.7. Страница уведомлений показывает список событий**
- Роль: клиент с полученными уведомлениями.
- Действие: открыть страницу «Уведомления» из шапки.
- Ожидаемый результат: видны события с датой; у непрочитанных нет пометки
  «прочитано»; количество в счётчике совпадает с числом непрочитанных.
- Результат: OK. Список уведомлений отображается, есть дата и текст события. Счётчик непрочитанных в шапке соответствует числу непрочитанных уведомлений.

**2.8. Уведомление помечается прочитанным** **[два окна]**
- Роль: клиент (окно 1) и администратор (окно инкогнито).
- Действие: администратор отменяет запись клиента; клиент открывает страницу
  «Уведомления» и открывает это уведомление.
- Ожидаемый результат: счётчик непрочитанных в шапке уменьшился, уведомление
  получило пометку «прочитано».
- Результат: OK. После отмены администратором у клиента увеличился счётчик непрочитанных. При отметке уведомления прочитанным счётчик уменьшился, уведомление стало прочитанным.

**2.9. Оформление записи прервано на промежуточном шаге**
- Роль: клиент.
- Действие: начать запись, выбрать слот, дождаться подтверждения, затем
  уйти на другую страницу или закрыть окно, вернуться позже.
- Ожидаемый результат: запись не создаётся «сама собой»; при возвращении
  не остаётся занятым удержанный слот либо сервис показывает, что слот
  освобождён.
- Результат: OK. Прерванная запись сама собой не создалась. Удержанный слот освободился по истечении таймера удержания (появляется текст «Время выбора истекло — выберите слот заново», список слотов перезагружается); после возвращения слот снова свободен.

## 3. Администратор

**3.1. Открыть админ-панель под администратором**
- Роль: администратор.
- Действие: открыть адрес админ-панели.
- Ожидаемый результат: открывается панель с вкладками «Записи», «Услуги»,
  «Мастера»; гость и клиент на этом адресе панель не открывают (см. раздел 4).
- Результат: OK. Под администратором открылась панель с вкладками «Записи», «Услуги», «Мастера». Вкладки переключаются, данные загружаются.

**3.2. Администратор отменяет запись клиента** — сценарий из отчёта Task_4
**[два окна]**
- Роль: администратор (окно 1) и клиент (окно инкогнито).
- Действие: заполнить запись клиента на будущее время; во вкладке «Записи»
  выбрать эту запись и отменить её, указав причину.
- Ожидаемый результат: запись в панели получает статус «отменена»; у клиента
  запись в кабинете получила пометку «запись отменена салоном», счётчик
  уведомлений увеличился, в уведомлении видно название записи и вследствие —
  причину.
- Результат: OK. Администратор отменил запись №10 на 13 октября, 10:00 с причиной «Мастер заболел». В панели запись получила статус «Отменена салоном»; в кабинете клиента — пометка «Отменена салоном», счётчик вырос с 0 до 1, пришло уведомление «Запись №10 на 13 октября, 10:00 к мастеру Артём Волков отменена администратором. Причина: Мастер заболел.»

**3.3. Администратор переносит запись клиента** **[два окна]**
- Роль: администратор (окно 1) и клиент (окно инкогнито).
- Действие: во вкладке «Записи» перенести запись клиента на другой свободный
  слот того же мастера.
- Ожидаемый результат: время изменилось в панели и в кабинете клиента, слот
  на прежнее время освободился, клиент получил **одно** уведомление с новым
  временем.
- Результат: OK. Перенос выполнен на другой свободный слот того же мастера: новое время отобразилось в панели и в кабинете клиента, прежний слот освободился, пришло одно уведомление с новым временем.

**3.4. Перенос на то же время или соседний свободный слот (регрессия)** —
проверка из журнала разработки
- Роль: администратор.
- Действие: перенести запись на время, которое она уже занимает, и на соседний
  свободный слот.
- Ожидаемый результат: перенос на то же время завершается без ошибки либо
  явно сообщает, что время не изменилось; соседний свободный слот переносится
  успешно, без ложного «время занято».
- Результат: OK. Перенос на текущее время завершился без ошибки (время осталось прежним), перенос на соседний свободный слот прошёл успешно — ложного «время занято» не возникло.

**3.5. Создание записи поверх занятого времени**
- Роль: администратор.
- Действие: во вкладке «Записи» создать запись нормированно на время, которое
  уже занято у мастера.
- Ожидаемый результат: сервис показывает предупреждение о пересечении и создаёт
  запись только после явного подтверждения.
- Результат: OK. При попытке создать запись на занятое время сервис показал занятые окна и предупреждение; запись создалась только после включения явного подтверждения наложения.

**3.6. Отключить услугу, с которой связаны старые записи**
- Роль: администратор.
- Действие: во вкладке «Услуги» выключить активную услугу, у которой есть
  исторические записи.
- Ожидаемый результат: услуга исчезает из выбора клиентов на лендинге и в форме
  записи, но сохраняется в карточках существующих записей (в кабинете клиента
  и панели админки).
- Результат: OK. Отключённая услуга пропала из выбора на лендинге и в форме записи, но осталась в карточках уже созданных записей в кабинете клиента и в панели.

**3.7. Добавить мастера с графиком и услугами**
- Роль: администратор.
- Действие: во вкладке «Мастера» добавить мастера: указать имя, e-mail, пароль,
  специализацию, услуги и расписание на 7 дней.
- Ожидаемый результат: новый мастер появляется в списке на лендинге, его услуги
  доступны для записи, свободные слоты соответствуют заданному графику.
- Результат: OK. Новый мастер появился на лендинге, его услуги доступны для записи, свободные слоты соответствуют заданному на 7 дней графику.

**3.8. Изменить график мастера и услуги**
- Роль: администратор.
- Действие: во вкладке «Мастера» изменить расписание действующего мастера
  (например, сделать выходной день рабочим) и состав его услуг.
- Ожидаемый результат: обновления видны в форме записи: новые дни/слоты
  появляются, услуги, снятые с мастера, перестают предлагаться.
- Результат: OK. После смены графика (выходной стал рабочим) в форме записи появились новые дни и слоты; услуги, снятые с мастера, перестали предлагаться.

**3.9. Отключить мастера**
- Роль: администратор.
- Действие: во вкладке «Мастера» выключить активного мастера.
- Ожидаемый результат: мастер исчезает из выбора клиентов; существующие записи
  к нему сохраняются и видны в панели.
- Результат: OK. Отключённый мастер исчез из выбора клиентов; его существующие записи сохранились и по-прежнему видны в панели.

**3.10. Создать услугу и убедиться, что она появилась на лендинге**
- Роль: администратор.
- Действие: во вкладке «Услуги» создать услугу с названием, длительностью
  и ценой.
- Ожидаемый результат: новая услуга появляется на лендинге (после перезагрузки)
  и в форме записи.
- Результат: OK. Созданная услуга с названием, длительностью и ценой появилась на лендинге после перезагрузки и в форме записи.

## 4. Безопасность

**4.1. Клиент открывает адрес админ-панели вручную** — сценарий из отчёта Task_4
- Роль: обычный клиент (роль `client`).
- Действие: войти под клиентом и ввести в адресной строке адрес админ-панели.
- Ожидаемый результат: сервис отказывает в доступе из-за неподходящей роли —
  на экране текст ошибки 403 («доступ запрещён»); данных админки нет.
- Результат: OK. Клиент по адресу `#/admin` увидел экран «Доступ закрыт» с текстом «Административная панель доступна только администратору. Вы вошли как oleg@example.com (клиент).» Данных админки нет. Прямой запрос `/api/admin/services` вернул 403 «Это действие доступно только с ролью admin.»

**4.2. Клиент обращается к админ-API напрямую** **[два окна]**
- Роль: обычный клиент.
- Действие: из инструментов разработчика (или второго окна) отправить запрос
  к админ-эндпоинту со своим токеном (например, список услуг админки).
- Ожидаемый результат: сервер возвращает 403; список услуг админки не получен.
- Результат: OK. Прямой запрос к `/api/admin/services` с токеном клиента вернул 403 «Это действие доступно только с ролью admin.»; список не получен.

**4.3. Гость обращается к админ-API без токена**
- Роль: гость.
- Действие: без входа отправить запрос к админ-эндпоинту.
- Ожидаемый результат: сервер возвращает 401 (не авторизован), данные не
  передаются.
- Результат: OK. Запрос к `/api/admin/services` без токена вернул 401 «Нужно войти в аккаунт.»; данные не переданы.

**4.4. Редактирование профиля мастера не затирает данные (регрессия)** —
проверка из журнала разработки
- Роль: администратор.

## Находки после проверки сервиса

Заполняется в степе «Исправляем ошибки после тестирования»: сюда переносятся
сценарии с расхождением «ожидали / увидели» и распределяются по группам.

### 1. Проблемы, которые портят данные или открывают чужую информацию
(пусто)

### 2. Проблемы, которые мешают пользоваться сервисом

- **Сетевая ошибка при обращении к API не обрабатывалась (клиент).**
  Ожидали: при обрыве связи с сервером пользователь увидит понятное сообщение,
  а экран не «зависнет».
  Увидели: при потере связи (например, во время перезапуска сервера) нажатие
  «Отменить запись» не давало реакции — сообщения не было, список не обновлялся.
  Причина: общий помощник запросов `api()` вызывал `fetch` без `try/catch`;
  при сетевой ошибке промис отвергался, и ошибка нигде не перехватывалась.
  Исправление: вызов `fetch` обёрнут в `try/catch`, при сетевой ошибке
  возвращается ответ той же формы с текстом «Нет связи с сервером. Проверьте
  подключение и обновите страницу.»; в маршрутизаторе добавлен запасной экран
  «Страница не загрузилась».
  Проверка: при выключенном сервере вместо бесконечной загрузки появляется
  сообщение о потере связи; при работающем сервере все сценарии проходят как
  прежде (`npm run check` — 134/134).
