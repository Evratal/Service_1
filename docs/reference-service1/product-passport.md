# Паспорт продукта

## Название и суть

**Сервис записи на услуги** — веб-сервис, в котором клиент сам выбирает мастера и удобное время записи, а администратор ведет расписание в единой панели вместо звонков и переписки.

## Цель и задачи

**Цель:** автоматизировать запись клиентов к мастерам и избавить бизнес от ручного учета записей по телефону и в переписке.

**Задачи:**

- Позволить клиенту самостоятельно выбирать мастера, услугу и время.
- Исключить двойную запись на один и тот же слот.
- Предоставить администратору единую панель для управления расписанием, услугами, мастерами и записями.
- Снизить количество ручных действий администратора и потерю записей.

## Целевая аудитория

- **Клиенты 20–45 лет**, которые привыкли решать бытовые задачи онлайн и готовы записываться через сайт, если это быстрее звонка.
- **Администратор и мастера бизнеса**, которые сейчас ведут запись вручную — по телефону и в переписке.

## Функции для пользователя сервиса (клиента)

- **Функция 1 — регистрация и вход по e-mail, включая восстановление пароля.**
  Потребность: получить доступ к личному кабинету без сложной настройки.
- **Функция 2 — просмотр списка мастеров и услуг.**
  Потребность: выбрать подходящего мастера и услугу, не уточняя это по телефону.
- **Функция 3 — просмотр свободных слотов в календаре.**
  Потребность: увидеть удобное время, не дожидаясь ответа администратора.
- **Функция 4 — запись в несколько кликов.**
  Потребность: записаться быстро, не заполняя длинные формы.
- **Функция 5 — просмотр и отмена собственных записей в личном кабинете.**
  Потребность: управлять своей записью самостоятельно, без звонка администратору.
- **Функция 6 — лендинг сервиса со списком услуг и преимуществами.**
  Потребность: узнать об услугах и записаться без звонка и регистрации на первом шаге.

## Функции для владельца/администратора сервиса

- **Функция 1 — админ-панель с управлением услугами и мастерами.**
  Потребность: обновлять список без обращения к разработчику.
- **Функция 2 — просмотр и управление всеми записями клиентов.**
  Потребность: видеть полную загрузку и вручную корректировать расписание при необходимости.
- **Функция 3 — разграничение доступа по ролям (`admin` / `user`).**
  Потребность: чтобы клиент видел только свои записи, а не записи других клиентов.
- **Функция 4 — управление расписанием мастера: рабочие часы, перерывы, выходные дни.**
  Потребность: точно описать, когда мастер принимает клиентов, и не открывать лишние слоты.
- **Функция 5 — ручное освобождение и перенос слотов.**
  Потребность: быстро исправить расписание при отмене или переносе визита.

## Сценарии использования

### Сценарий 1. Первая запись клиента

Клиент заходит на сайт → регистрируется по e-mail → выбирает мастера и услугу → просматривает свободные слоты в календаре → подтверждает запись → получает подтверждение в личном кабинете.

### Сценарий 2. Конфликт слотов

Два клиента одновременно открывают один и тот же свободный слот → первый клиент подтверждает запись → слот помечается занятым → второй клиент при попытке подтвердить видит сообщение, что время уже занято, и обновленный список свободных слотов.

> Это готовый тест-кейс: в пятом уроке сценарий прогоняется вручную, чтобы проверить, что бэкенд действительно не допускает двойную запись на один слот.

### Сценарий 3. Администратор управляет расписанием

Администратор заходит в админ-панель → открывает список записей на день → видит, что клиент отменил визит → вручную освобождает слот → слот снова становится доступен для записи другим клиентам.

### Сценарий 4. Клиент отменяет запись

Клиент открывает личный кабинет → видит список своих записей → выбирает будущую запись → нажимает «Отменить» → слот освобождается и снова появляется в общем календаре свободных слотов.

### Сценарий 5. Клиент пытается посмотреть чужую запись

Клиент отправляет запрос чужой записи или открывает админ-панель → API проверяет роль и владельца записи → доступ отклоняется с ошибкой 403 → клиент видит только свои данные.

## Ограничения и риски

### Ограничения

- Онлайн-оплата не предусмотрена: клиент оплачивает услугу на месте.
- Сервис рассчитан на один бизнес с несколькими мастерами, а не на маркетплейс из нескольких компаний.
- Уведомления приходят только внутри личного кабинета; интеграция с e-mail или Telegram не входит в MVP.
- Нет мобильного приложения — только адаптивный веб-интерфейс.

### Риски

- **Потеря данных.** Файл SQLite хранится на сервере локально — при обновлении кода или сбое сервера данные можно потерять без отдельного бэкапа. *Закрывается в уроках 3 и 6: регулярный бэкап файла БД.*
- **Состояние гонки.** Два клиента одновременно пытаются занять один свободный слот. Если проверка доступности не реализована на уровне API, возможна двойная запись. *Закрывается в уроках 3 и 5: атомарная транзакция / `UNIQUE`-ограничение на слот + ручной прогон сценария.*
- **Ошибки в правах доступа.** Права прописаны в API вручную, без готовых механизмов вроде Supabase RLS — ошибка в проверке роли может дать клиенту доступ к чужим записям. *Закрывается в уроке 5: проверка роли `admin`/`user` на каждом эндпоинте и тест-кейс «доступ к чужой записи».*
- **Ошибки валидации на клиенте.** Некорректный ввод данных (e-mail, обязательные поля) приводит к потере заявки. *Закрывается в уроке 4: клиентская валидация форм и понятные сообщения об ошибках API.*
