## 2026-09-28 — Инициализация проекта и бэкенд записи (Task_2)

### Построено
- Прототип трёх экранов (`prototype/`) и каркас сервиса на Node.js + SQLite (`node:sqlite`).
- Регистрация и вход по e-mail с хешированием пароля (`scrypt`) и токенами доступа
  в `auth_tokens`; ограничение неудачных попыток входа (`login_attempts`).
- Каталог услуг и мастеров, загрузка из базы на лендинг.
- Бронирование: выбор услуги → мастера → свободного слота → подтверждение.
  Свободные слоты вычисляются на сервере из графика мастера (`schedules`),
  записей (`appointments`) и блокировок (`time_blocks`).
- Защита от двойной записи на трёх уровнях: проверка в API (код `409` с понятным
  сообщением), транзакция `BEGIN IMMEDIATE` и триггер пересечения в базе.
- Права доступа: роли `client` / `master` / `admin` в `user_roles`, проверка роли
  и владельца записи на каждом эндпоинте.

### Исправлено в процессе
- **Лишние слоты при длинных услугах.** Клиент мог выбрать время, которое не
  влезает до конца рабочего дня (начало позже `work_end − длительность`).
  Причина: при нарезке окон не проверялось, что визит полностью помещается
  в рабочий интервал мастера. Исправлено: обрезка слотов по фактическому концу
  рабочего дня.
- **Двойная запись при гонке.** Проверки доступности по чтению не хватало для
  одновременных запросов. Исправлено: `BEGIN IMMEDIATE` берёт блокировку записи
  сразу, а триггер в базе — окончательная гарантия (работает даже при вставке
  в обход API).

## 2026-10-09 — Админ-панель, уведомления и тестирование (Task_4)

### Построено
- **Миграция `002_notifications.sql`**: таблица `notifications` (kind, title,
  message, is_read, `appointment_id`), два индекса.
- **Админ-API** (`src/routes/admin.js`):
  - услуги — список, создание, изменение, включение/выключение (старая запись
    сохраняется в истории, из выбора клиентов услуга исчезает);
  - мастера — список, создание (вместе с учётной записью, услугами и графиком),
    изменение профиля, услуг и графика, включение/выключение;
  - записи — все записи с клиентами, услугами, мастерами.
- **Работа администратора с записью клиента** (`src/routes/appointments.js`):
  - создание записи за клиента (в т.ч. поверх занятого времени по явному
    подтверждению — `is_override`);
  - отмена записи с причиной (статус `cancelled_by_salon`);
  - перенос на другое время (`POST /:id/reschedule`) с проверкой доступности
    и возможностью override.
- **Уведомления** (`src/routes/notifications.js`, `src/notify.js`): счётчик
  непрочитанных в шапке, страница «Уведомления», пометка прочитанным. События
  создаются только для действий администратора над чужой записью; собственные
  действия клиента уведомлений не дают.
- **Фронтенд админки** (`public/assets/js/admin.js`): вкладки «Записи»,
  «Услуги», «Мастера» — карточки записей, отмена с причиной, перенос, запись
  клиента, CRUD услуг и мастеров, редактор графика. Скрипт подключён отдельным
  файлом из-за CSP (`script-src 'self'`).
- **Разграничение доступа**: гость на адресе админки → страница входа,
  обычный клиент → текст «403 — доступ запрещён», администратор → панель.
  На сервере возвращается `401`/`403` с проверкой роли на каждом эндпоинте.

### Исправлено в процессе сборки
- **Ложный конфликт при переносе записи.** Перенос «на своё же место» и на
  соседний свободный слот давал ошибку 409. Причина: расчёт свободных слотов
  учитывал саму переносимую запись как занятую. Исправлено: в
  `busyIntervals` / `computeFreeSlots` добавлен параметр `excludeAppointmentId`,
  чтобы запись не блокировала саму себя.
- **Сброс данных при редактировании профиля.** `updateUserProfile` обновлял все
  поля одним `UPDATE ... SET` и мог записать `NULL` в обязательные колонки, если
  клиент-мастер не заполнил имя. Исправлено: `SET` собирается динамически только
  из переданных полей.
- **Статус отмены чужим/салоном.** Ошибка теста, а не сервиса: ожидался
  `cancelled_by_admin`, фактический статус — `cancelled_by_salon`. Исправлен
  сценарий в `scripts/check-api.js` (повторные отмены и показ в личном кабинете
  работают корректно).
- **Смоук после правок.** Проверены на реальной базе: вход администратора,
  чтение услуг/клиентов/мастеров, счётчик уведомлений, отказ гостю (`401`) и
  клиенту (`403`) в админ-разделе.

## 2026-10-15 — Подготовка проекта к запуску на сервере (Урок 5.6)

### Построено
- **Инструкция сборки `Dockerfile`**: базовый образ `node:24-slim` — та же
  мажорная версия Node, что и на компьютере разработчика (v24.x). Зависимостей
  у проекта нет (`node:sqlite` встроен в Node), поэтому установка пакетов в
  сборке не выполняется.
- **`.dockerignore`**: в образ не копируются файл базы (`data/`), секреты
  (`.env`), `node_modules/`, история Git, материалы курса и рабочие документы
  `docs/`. Главное — файл базы не уезжает в сборку и не перезаписывает боевую.
- **`docker-compose.yml`**: описание запуска для Coolify — сборка по
  `Dockerfile`, том `app_data` смонтирован в `/app/data`, переменные окружения,
  `TRUST_PROXY=1` (сервис стоит за прокси Coolify).
- **Миграции применяются при запуске приложения**, а не отдельной командой.
  Логика вынесена в `src/migrations.js`; `src/server.js` вызывает
  `applyMigrations(db)` до открытия порта (вместо прежней проверки «миграции
  применены»). Скрипт `scripts/migrate.js` использует ту же функцию.

### Файл базы
База лежит в отдельной папке `data/` (в образ не копируется), путь берётся из
настройки `DB_FILE` (по умолчанию `./data/app.db`). На сервере каталог
`/app/data` подключён отдельным томом, поэтому данные переживают пересборку
контейнера. Папка создаётся автоматически при первом запуске, на чистом сервере
база создаётся миграциями при старте приложения.

### Настройки, которые нужно задать на сервере
Обязательные:
- `NODE_ENV=production`
- `PORT=3000`
- `DB_FILE=/app/data/app.db`
- `TRUST_PROXY=1` — сервис за прокси Coolify.

С разумным значением по умолчанию (можно не задавать):
- `TOKEN_TTL_HOURS=24`
- `RATE_LIMIT_ATTEMPTS=5`
- `RATE_LIMIT_WINDOW_MIN=15`
- `HOLD_TTL_SEC=300`

Позже, при подключении входа через «Яндекс», добавятся идентификатор и секрет
приложения и адрес возврата — задаются только в панели на сервере, в репозитории
их быть не должно.

  поэтому Traefik отдавал временный самоподписанный сертификат, а не боевой.

- `https://portfolio-evratal-1.ru/` → `200`, сертификат Let's Encrypt валиден.

- Контейнер запущен, миграции применены при старте, том `/app/data` подключён.

## 2026-10-16 — Вход через «Яндекс» (Урок 5.6, шаг 8)

### Построено
- **Миграция `003_oauth_provider.sql`.** К таблице `users` добавлены колонки
  `provider` и `provider_id` (внешняя учётная запись) и частичный уникальный
  индекс `(provider, provider_id)`. Колонки добавляются через `ALTER TABLE`, а не
  пересозданием таблицы: на `users` ссылаются внешними ключами роли, мастера,
  записи и токены, и `DROP TABLE` унёс бы связанные данные.
- **Модуль `src/yandex.js`** — единственное место, где приложение говорит с
  «Яндексом»: обмен кода на токен и чтение профиля (почта, имя). Токен «Яндекса»
  нигде не сохраняется, у всех запросов есть таймаут.
- **Маршруты входа.** `GET /api/auth/yandex` отправляет на страницу согласия
  «Яндекса» с одноразовым `state` (в памяти процесса, живёт 10 минут — защита от
  подмены запроса). `GET /api/auth/yandex/callback` принимает возврат и в любом
  случае отвечает перенаправлением на сайт: результат передаётся во фрагменте
  адреса (`#/login?yandex=…`), поэтому токен не попадает в логи сервера и в
  заголовок `Referer`.
- **Связывание аккаунтов** (`upsertExternalUser`): ищем по внешней учётной записи,
  затем по почте (привязываем к существующему аккаунту, сохраняя роли), иначе
  заводим нового клиента без пароля. Заблокированный аккаунт не привязывается.
- **Обработка перенаправлений в `src/app.js`:** обработчик может вернуть
  `{ redirect }`, и `handleApi` отвечает `302` вместо JSON.
- **Клиентская часть:** кнопка «Войти через Яндекс» на экране входа и в блоке
  регистрации (белый фон, чёрный текст, фирменный знак — по правилам оформления
  кнопки «Яндекса»), разделитель «или», ссылка «Забыли пароль?» с пояснением, что
  вход можно выполнить через «Яндекс» без пароля. Результат возврата разбирается
  из адреса, токен убирается из адресной строки.
- **Настройки.** `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` —
  задаются только в панели сервера; если хотя бы одно значение пусто, вход через
  «Яндекс» выключен. Значения описаны в `.env.example`.

### Почему так, а не иначе
- Пароль у внешних пользователей не хранится: в `password_hash` пишется пустая
  строка (колонка `NOT NULL`), а вход по паролю для такого аккаунта отсекается —
  вместо сохранённого хеша всё равно считается ложный, чтобы по времени ответа
  нельзя было отличить аккаунт без пароля.
- Результат возврата передаётся во фрагменте адреса, а не в `?query`: фрагмент не
  уходит на сервер, поэтому одноразовый токен не оседает в логах и в `Referer`.

### Проверено
- Новый набор `scripts/check-yandex.js` — **25 проверок**: начало входа, отказ
  пользователя, защита `state` (чужой и повторный), успешный вход, повторный вход,
  привязка к существующему аккаунту, заблокированный аккаунт, сбой «Яндекса».
  «Яндекс» заменён заглушкой поверх настоящего `fetch`, поэтому проверяется именно
  наша логика, без сети и настоящих ключей. Скрипт входит в `npm run check`.
- Прежние наборы остались зелёными: `check.js` — 39, `check-api.js` — 134,
  `check-web.js` — 17.

### Что нужно сделать на сервере (не в репозитории)
- Зарегистрировать приложение в кабинете https://oauth.yandex.ru, включить ему
  права на e-mail и имя, указать адрес возврата
  `https://portfolio-evratal-1.ru/api/auth/yandex/callback`.
- Добавить переменные `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`,
  `YANDEX_REDIRECT_URI` в переменные окружения приложения в Coolify.

### Проверено на боевом адресе
- Каталог приходит из базы (6 услуг, 3 мастера); страница по HTTPS, смешанного
  содержимого нет.
- Вход по паролю и вход через «Яндекс» (см. запись выше).
- Запись создаётся с верным временем: часовой пояс `Europe/Moscow`, сдвига нет.
- Два клиента на один слот: второй получает `409` с понятным текстом, двойной
  записи нет.
- Удержание слота берётся и освобождается (`HOLD_TTL_SEC`).
- Администратор отменяет запись, у клиента появляется уведомление с верной датой.
- Гость в админ-API → `401`, клиент → `403`.

### Что нашлось при приёмке
- Боевая база была **не наполнена**: салон, услуги и мастера отсутствовали, лендинг
  открывался пустым. Сидер в образ не входит, и обычный `scripts/seed.js` не
  запускается на базе с пользователями. Исправлено: `scripts/seed.js` влит в
  контейнер и выполнен с ключом `--fresh` — появились салон «TOP BRO», 6 услуг,
  3 мастера с графиком, администратор и клиенты; ранее созданный
  `evratal@yandex.ru` сохранён.

### Как погасить сервер
1. Скачать файл базы (см. копию выше), если данные жалко.
2. Удалить сервер в панели провайдера — именно удалить, а не выключить:
   посуточная тарификация продолжает списывать деньги за выключенный сервер.
   После удаления проверить, что услуги нет в списке и не осталось автопродления.
